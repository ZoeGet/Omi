# OmiPet

源码提交、隐私排除和逐批推送要求见 [CONTRIBUTING.md](CONTRIBUTING.md)。本地安装包、实验日志和设备凭证不属于源码提交范围。

OmiPet 是一个面向桌面陪伴场景的开源软硬件项目：它以 ESP32-S3 为核心，集成横向显示的彩色 LCD、温湿度传感器、灯带、蜂鸣器和数字麦克风，逐步实现桌面宠物、环境感知和离线语音交互。

> **English** — OmiPet is an open-source desktop companion project built around an ESP32-S3. It combines a landscape-oriented color LCD, environmental sensing, addressable LEDs, a buzzer, and an I²S digital microphone with an experimental offline voice interaction path.

## 项目状态 / Project Status

当前项目包含设备固件、Windows 控制中心和 Codex 生命周期采集器。基础硬件与语音路径已有实测；桌面/无线能力在默认关闭的隔离固件中启用：

- NV3007 `142 × 428` LCD 基础驱动和桌面宠物 UI。
- AHT20 温湿度采集、CRC 校验和整机热影响补偿。
- `13` 颗 WS2812B-2020-V6 灯带驱动。
- 灯带常亮颜色、彩虹、呼吸、左右往返扫描和中心扩散回收动效，并支持离线语音切换。
- 无源蜂鸣器驱动。
- Wi-Fi 异步连接和手机网页配网门户。
- Wi-Fi 连接后通过 NTP 获取本地时间和日期；断网时显示占位符，不使用编译时间或假时间。
- BAT_ADC 电池电压采样和单节锂电估算电量显示；百分比仍需结合实测电池曲线校准。
- ICS-43434 原始 I²S 采集、RMS 音量分析、自适应语音活动检测和 16-bit PCM 音频帧适配。
- ESP-SR v1.2.0 中文 MultiNet `mn6_cn`，当前 47 条短语、命令 ID 1–17，包含亮度、颜色、动效与语音开启配对。
- 唯一 Windows 上位机 `Tools/Desktop`：首页 USB / Wi-Fi 连接、灯光与五种监控状态配置、配对管理、首次监控配置向导、托盘和持久化主题。

离线语音识别与调灯无需 Wi-Fi；联网是配对/无线控制和 NTP 的条件，不是语音识别的前提。

当前固件不启用 WakeNet，也不把现成唤醒词冒充为产品唤醒词；“老鼠狒狒”通过中文 MultiNet 自定义命令词表作为唤醒入口，仍属于低延迟和误识别特性待继续验证的实验方案。

语音配对/重新配对入口（需升级配套固件与模型；语音开窗、重配及无线控制已实测，异常边界待验）：设备联网后说“老鼠狒狒”，听到确认音再说“开启配对模式”，显示当前 IP 和六位新码；普通重启不开窗。软件可首次配对或主动重配，后者成功后旧凭据失效，日常无需 USB。窗口/异常恢复规则见 [PAIRING.md](Tools/DeviceBridge/PAIRING.md)。

> **English** — The current firmware includes the display, environmental sensor, LED strip, passive buzzer, Wi-Fi provisioning, verified ICS-43434 I²S capture, and an ESP-SR v1.2.0 Chinese MultiNet `mn6_cn` command-recognition path using the separate model partition. WakeNet is disabled; “老鼠狒狒” is registered as a custom MultiNet phrase and remains an experimental wake-entry strategy whose latency and false-trigger behavior still require validation.

## 麦克风与 I²S / Microphone and I²S

当前固件使用 ESP32-S3 Arduino 框架内置的 ESP-IDF 旧版 I²S 驱动接口 `<driver/i2s.h>`，没有额外安装 ICS-43434 专用库。驱动直接调用 `i2s_driver_install()`、`i2s_set_pin()` 和 `i2s_read()`。

> **English** — The microphone driver uses the ESP-IDF I²S driver bundled with the ESP32-S3 Arduino framework. No dedicated ICS-43434 library is required.

### 硬件连接 / Hardware mapping

| ICS-43434 信号 / Signal | ESP32-S3 GPIO | 说明 / Description |
| --- | ---: | --- |
| `SCK` / BCLK | `GPIO5` | ESP32-S3 输出位时钟 / Bit clock generated by ESP32-S3 |
| `WS` / LRCLK | `GPIO6` | 字选择时钟 / Word-select clock |
| `SD` | `GPIO7` | 麦克风串行数据输出 / Microphone serial data output |
| `LR` | 由硬件电阻配置 | 决定左/右声道槽 / Selects the left or right I²S slot |

### 当前有效声道 / Active channel

**当前固件明确使用 I²S 右声道槽（`MicChannel::Right`）。**

这是根据当前实物测试确认的：原始双槽数据中只有右声道槽出现非零采样，左声道槽为零。因此 `Firmware/src/main.cpp` 会显式调用：

```cpp
OmiPetAudio::microphone.begin(
    OmiPetAudio::kMicDefaultSampleRateHz,
    OmiPetAudio::MicChannel::Right);
```

对应代码位于 [`Firmware/src/main.cpp`](Firmware/src/main.cpp) 和 [`Firmware/include/ics43434_mic.h`](Firmware/include/ics43434_mic.h)。如果更换 PCB、修改 `LR` 电阻或更换麦克风装配方向，需要重新确认有效声道，并同步修改 `MicChannel::Right`。

> **English** — The current firmware explicitly uses the **right I²S slot** (`MicChannel::Right`). This was verified on the assembled hardware because the right slot contains non-zero samples while the left slot remains zero. Re-check the slot if the PCB `LR` configuration or microphone assembly changes.

### 当前音频参数 / Current audio parameters

- 采样率：`16 kHz` / Sample rate: `16 kHz`
- 接收槽宽：`32-bit` / Receive slot width: `32-bit`
- 有效数据：ICS-43434 的 `24-bit` 数据，固件右移 8 位后用于音量分析 / 24-bit microphone data shifted by 8 bits for level analysis
- 音量窗口：约 `50 ms` / Level window: approximately `50 ms`
- 输出指标：`avg_abs`、`rms`、`peak`、`noise`、`threshold`、`speech`


### 语音交互状态 / Voice interaction state

当前固件使用 `16 kHz`、`16-bit`、单声道 PCM，将每次 `160` 个采样点的输入帧送入 AFE；AFE 以约 `512` 个采样点的输出帧驱动中文 MultiNet `mn6_cn`。词表包含自定义入口“老鼠狒狒”（ID `1`）、亮度（ID `2/3`）、颜色与动效（ID `4–16`）及“开启配对模式”（ID `17`）。识别到入口后，状态机播放约 `180 ms` 的三段式确认反馈，进入最长 5 秒的 `LISTENING` 等待已配置的灯带或配对命令，同时用独立的白色跑马灯表示已唤醒；命令执行或等待超时后结束这一临时提示。

### 灯带颜色与动效 / LED Colors and Effects

唤醒后说出颜色或动效命令即可切换灯带。颜色命令会保留原本的本地动效，不会强制切换成常亮；唤醒期间的白色跑马灯是独立提示，不会把后续“蓝色灯光”变成蓝色跑马灯。彩色灯光使用彩虹动效，呼吸灯、跑马灯和扩散灯由主循环以非阻塞方式推进，使用约 `12 ms` 的时间驱动帧。三个由命令启动的动效默认使用纯色：呼吸灯为纯蓝、跑马灯为纯绿、扩散灯为纯红；动画只改变亮度，不把其他颜色混入当前颜色。跑马灯和扩散灯始终保留全灯带底光，并用连续渐变高光移动，避免灯珠逐颗跳变或完全熄灭。支持的动效说法包括“彩色”“彩色灯光”“彩色灯”“呼吸灯”“跑马灯”“扩散灯”；RGB 语音词条已删除；颜色命令支持“红色灯光/红色灯”等表达；还支持“开灯”“开启灯光”“一直亮”“关灯”和“关闭灯光”。亮度命令仍以 `16/255` 为步长调整全局亮度，“调亮一点/调暗一点”中的“调”使用拼音 `tiao`。

> **English** — After the custom wake entry, use colorful lights, breathing lights, running lights, or expanding lights. Color commands keep the active effect instead of forcing solid mode. The default effect colors are pure blue for breathing, pure green for running lights, and pure red for expanding lights; animation changes brightness without mixing hues. Running and expanding effects keep a base light on every pixel and add a smooth moving gradient. The brightness commands use `tiao` for 调, as in `tiao liang yi dian` and `tiao an yi dian`.

AFE 和 I²S 始终持续运行，但 VAD 只在检测到语音以及语音结束后的 `1.2 s` 尾窗内调用 MultiNet；这样避免待机时持续推理造成 CPU 调度和看门狗风险，同时尽量保留词尾。该门控策略不会承诺每次都在说话过程中返回，MultiNet 本身仍可能需要积累判定窗口。

> **English** — The firmware uses `16 kHz`, `16-bit`, mono PCM. It feeds `160`-sample input frames into AFE, which produces approximately `512`-sample frames for Chinese MultiNet `mn6_cn`. The current list has 47 phrases across command IDs 1–17: wake entry, brightness, colors/effects, and opening pairing mode. After detection, the state machine plays an approximately `180 ms` three-phase acknowledgement and listens for configured phrases such as “亮一点”, “暗一点”, or “开启配对模式”; this is finite-vocabulary recognition, not open-ended speech understanding.

I²S and AFE remain active continuously, while VAD gates MultiNet detection to speech activity plus a `1.2 s` hangover. This reduces idle inference load and watchdog risk while preserving phrase endings; it does not guarantee that MultiNet returns before the speaker finishes a phrase.

确认音播放期间以及结束后的 200 ms 内，VAD 会暂时抑制语音状态更新，但 I²S/PCM 仍持续采集，避免蜂鸣器回采触发语音开始事件。

> **English** — During the acknowledgement tone and for 200 ms afterward, VAD state updates are temporarily suppressed while I²S/PCM capture continues, preventing buzzer feedback from triggering speech-start events.

## 语音技术栈与唤醒词架构 / Voice Stack and Wake Phrase Architecture

### 技术栈 / Technology stack

当前语音功能采用 **Arduino 应用层 + ESP-IDF 底层 + ESP-SR 语音组件**，不是只依赖 Arduino 库的纯软件实现：

| 层级 / Layer | 当前实现 / Current implementation |
| --- | --- |
| 构建系统 / Build system | PlatformIO，`framework = arduino, espidf` |
| 应用逻辑 / Application logic | Arduino `setup()`/`loop()`、GPIO、灯带、蜂鸣器、UI 和状态机 |
| 音频底层 / Audio layer | ESP-IDF 旧版 I²S 驱动 `<driver/i2s.h>`，驱动 ICS-43434 |
| 语音前端 / Speech front end | ESP-SR AFE，负责音频预处理、AGC 和 VAD |
| 命令识别 / Command recognition | ESP-SR v1.2.0 中文 MultiNet `mn6_cn` |
| 模型存储 / Model storage | `model` 分区中的 SPIFFS 模型镜像 |
| 内存与芯片 / Memory and chip | ESP32-S3-WROOM-1-N16R8，OPI PSRAM，模型和 AFE 缓冲优先使用 PSRAM |

Arduino 负责设备业务和主循环；ESP-IDF 提供 I²S、FreeRTOS 调度和底层硬件接口；ESP-SR 提供 AFE、MultiNet 接口和语音模型。三者是同一份固件中的分层协作关系，不是互相替代的三套方案。

> **English** — The voice feature uses an **Arduino application layer + ESP-IDF low-level APIs + ESP-SR speech components**. Arduino handles `setup()`/`loop()`, device behavior, LEDs, buzzer, UI, and state transitions. ESP-IDF supplies I²S, scheduling, and hardware-level services. ESP-SR supplies the AFE, VAD, MultiNet interfaces, and speech models. This is an Arduino-based application built on the ESP-IDF component layer, not an Arduino-only library implementation.

### 音频处理流程 / Audio processing pipeline

```text
ICS-43434 I²S
    ↓
ESP-IDF I²S RX（GPIO5/GPIO6/GPIO7，16 kHz，32-bit slot）
    ↓
右声道槽提取与 PCM16 转换
    ↓
160-sample PCM frame queue
    ↓
ESP-SR AFE（持续 feed/fetch，包含 VAD）
    ↓
VAD 语音窗口 + 1.2 s 尾窗门控
    ↓
ESP-SR MultiNet `mn6_cn`
    ↓
命令 ID → 唤醒状态机、灯带业务或本机配对请求
```

I²S、PCM 队列和 AFE 会持续运行，但 MultiNet 只在检测到语音活动或最近 `1.2 s` 的语音尾窗内进行判定。门控使用 `main.cpp` 的 RMS、自适应噪声底与连续窗口迟滞；AFE 自带 VAD 虽开启，但不是 `allowDetection` 的直接输入。这样可以避免空闲时持续运行 MultiNet 引起 CPU 调度压力和看门狗风险，同时尽量保留词尾音频。

### “老鼠狒狒”如何实现 / How “老鼠狒狒” is implemented

当前并没有把“老鼠狒狒”写成 WakeNet 模型名称，也没有把它伪装成官方唤醒词。它是中文 MultiNet 命令词表中的一个自定义拼音短语：

```text
1 lao shu fei fei
```

个人配置位于 `Firmware/include/voice_command_config.h`。构建前，`Firmware/scripts/generate_model.py` 会先解析这个文件，将全部命令生成到当前构建目录的 `multinet_commands_cn.txt`，再把词表复制到 `target/fst/commands_cn.txt`，生成并加入 PlatformIO 的 `model` 分区镜像。运行时，`Firmware/src/multinet_command_recognizer.cpp` 会通过 ESP-SR 的命令词 API 注册同一组拼音和命令 ID，因此应用固件与模型使用同一份配置。

识别到命令 ID `1` 后，主循环将它解释为自定义唤醒入口：

1. 清空上一段 AFE/MultiNet 上下文；
2. 通知 `VoiceController` 进入 `LISTENING`；
3. 播放非阻塞双音确认反馈；
4. 在 5 秒监听期内接受 ID `2–17` 的已配置命令；
5. ID `2/3` 调整亮度 `16/255`，ID `4–16` 控制颜色/动效，ID `17` 请求限时配对窗口；命令完成或超时后回到持续监听。无线功能未启用或未就绪时，配对请求返回 `PAIR UNREADY`。

命令词的唯一修改入口是 `Firmware/include/voice_command_config.h`。修改或新增数组项即可维护唤醒词、同义表达和后续命令；不要直接修改构建目录内的 `multinet_commands_cn.txt`，也不要修改自动生成的 `Firmware/include/generated_multinet_commands.h`。构建检查会拒绝空配置、重复短语、非正 ID、非法拼音、超过 MultiNet 长度/数量上限的配置，并确保当前运行时必需的 ID `1–17` 与头文件一致，且 ID `1` 只有一条短语。

更换或新增步骤：编辑 `Firmware/include/voice_command_config.h` → 修改/增加 `{命令ID, "无声调拼音"}` → 重新构建 → PlatformIO 自动同步词表、生成运行时表并把 `model.bin` 加入烧录列表 → 将应用固件和模型分区一起烧录 → 查看 `[ASR] continuous experiment wake_id=1 phrase=...` 日志并实测。新增命令词会自动注册，但要让设备执行新的业务动作，还必须在 `Firmware/src/main.cpp` 中为该命令 ID 增加业务分派；配置入口不会凭空生成未实现的业务逻辑。

因此，“唤醒词”在当前固件中准确的技术名称是：**MultiNet 自定义命令词入口**，而不是独立的 WakeNet 唤醒模型。

> **English** — “老鼠狒狒” is not a WakeNet model name and is not presented as an official wake word. It is registered as the custom Chinese MultiNet phrase `lao shu fei fei` with command ID `1`. The personal configuration entry is `Firmware/include/voice_command_config.h`; the build synchronizes every configured phrase to the model input, validates limits and IDs, generates the runtime table, and adds the model image to the PlatformIO flash list. New phrases are registered automatically, but a new command ID still needs a corresponding business handler in `Firmware/src/main.cpp`. Changing the tone-free pinyin requires rebuilding and reflashing both the application and the model partition, followed by recognition testing; it is not a runtime setting and arbitrary phrases are not guaranteed to work reliably. The accurate technical description is **a MultiNet custom command entry used as an experimental wake trigger**, not a standalone WakeNet model.

### 为什么不用现成 WakeNet / Why the supplied WakeNet model is not used

WakeNet 是专门的唤醒模型，但当前 ESP-SR 模型包中的现成模型对应固定唤醒短语，例如 `wn9_hiesp` 对应 `Hi ESP`。把配置中的字符串改成“老鼠狒狒”，不会改变神经网络已经训练好的识别目标；真正的自定义 WakeNet 需要与目标短语匹配的定制模型，并且还要重新完成模型打包、容量确认、误唤醒率和漏唤醒率验证。

本项目当前没有“老鼠狒狒”的定制 WakeNet 模型，而项目目标又明确要求自定义唤醒词，因此不能直接使用现成 WakeNet 冒充已经实现了目标词。当前配置明确关闭 WakeNet：`CONFIG_USE_WAKENET=n`，运行时 AFE 配置也设置 `wakenet_init = false`。

选择 MultiNet 自定义命令词作为实验入口，是因为它允许我们在现有中文 `mn6_cn` 模型上注册自己的拼音短语，不需要等待或伪造一个不存在的定制 WakeNet 模型。代价是 MultiNet 不是低延迟专用唤醒引擎：早期词表短测中，“老鼠狒狒”在语音结束后曾等待约 `1.1–1.3 s`；当前 47 词模型的延迟尚未完成统计，并且仍需继续验证误识别、误触发和长期稳定性。

> **English** — WakeNet is a dedicated wake-word model, but the bundled model is trained for fixed phrases such as `Hi ESP`. Changing a configuration string does not retrain the neural network. A real custom WakeNet phrase requires a matching custom model, followed by model packaging, capacity checks, false-trigger testing, and missed-wake testing. Because this project does not currently have a custom “老鼠狒狒” WakeNet model, WakeNet is explicitly disabled. MultiNet custom commands provide a workable offline experimental entry, but they are not a low-latency dedicated wake engine; an earlier phrase-list test observed about `1.1–1.3 s` after speech ended. The current 47-phrase model still needs latency and long-run statistics.

### 关键构建文件 / Important build files

- `Firmware/platformio.ini`：声明 Arduino + ESP-IDF 双框架、PlatformIO 环境和模型预构建脚本。
- `Firmware/CMakeLists.txt`：ESP-IDF 工程入口。
- `Firmware/src/CMakeLists.txt`：注册固件源文件并声明 `esp-sr` 组件依赖。
- `Firmware/sdkconfig.defaults`：启用 AFE、中文 MultiNet、模型分区、16 MB Flash 和 OPI PSRAM，并明确关闭 WakeNet。
- `Firmware/components/esp-sr`：ESP-SR v1.2.0 子模块，提供 AFE/MultiNet 头文件、库和模型工具。
- `Firmware/include/voice_command_config.h`：个人语音命令配置入口；集中维护命令 ID 和无声调拼音短语，ID `1` 为唤醒词，ID `2/3` 为亮度，ID `4–16` 为颜色和动效，ID `17` 为语音开启配对模式。
- `Firmware/include/led_controller.h`、`Firmware/src/led_controller.cpp`：分离的 WS2812B 硬件缓存 `Strip` 和非阻塞动画控制器 `EffectController`。
- `Firmware/scripts/check_multinet_commands.py`：构建前解析个人配置、同步词表、校验命令 ID/重复短语/容量，并生成 `Firmware/include/generated_multinet_commands.h`。
- 构建目录的 `multinet_commands_cn.txt`：自动生成的模型输入，不纳入版本管理；唯一配置入口仍是 `voice_command_config.h`。
- `Firmware/scripts/generate_model.py`：将 ESP-SR 模型和项目词表打包成 `model.bin`，并将其加入 PlatformIO 烧录流程。

这些文件共同组成当前语音架构；不能因为没有使用 WakeNet 就删除 `CMakeLists.txt`、`sdkconfig.defaults` 或整个 `esp-sr` 目录。

## Codex 状态采集实验 / Codex Monitoring Experiment

Windows 主机端工具见 [Tools/CodexMonitor](Tools/CodexMonitor/README.md)：通过本地 Hook 采集多会话生命周期与审批状态，提供隐私保护、回归测试和只读诊断。用户 Hook 现启用可回退的事件关联侧文件；只有新事件与真实宿主配对的会话可接纳为明确状态，过期且未接纳的历史记录保留在本地，不占当前设备视图名额。上位机可通过 USB 或已配对的 WSS 传输。

Windows 上位机统一在 [Tools/Desktop](Tools/Desktop/README.md)，使用 Tauri + React + Microsoft Fluent UI 界面和共享 Python 控制层；旧 Tk 程序已移除。界面参考 WinUI Gallery，模块化布局，设置页提供浅色、深色、跟随系统三张预览卡，切换后记住选择。首页统一选择 USB 串口或已配对 Wi-Fi 设备，支持本地灯光、Codex 监控、诊断、配对管理与设置；六位码 WSS 配对、重连认证及无线灯光/监控已接入隔离实验，用户确认拔掉 USB 后仍可无线控制。验证边界见 [PAIRING.md](Tools/DeviceBridge/PAIRING.md)。完整灯光及跨连接最终输出读回仍待接入。便携包唯一启动入口为 `Tools/Desktop/release/OmiPet/Omi.exe`。新用户通过程序内向导安装采集组件并完成 Codex Hook 信任，步骤见 [快速开始](Tools/Desktop/QUICK_START.md)，源码分层见 [Tools](Tools/README.md)。

USB/Wi-Fi 共用协议与主机工具见 [Tools/DeviceBridge](Tools/DeviceBridge/README.md)。当前支持监控灯效的隔离固件按五种状态读取可配置的颜色、亮度和动效，并保存到 NVS。默认无事件/完成/来源异常绿、运行红、等待操作黄；同一聊天由当前用户任务判定：运行红，当前任务结束且没有本任务待回复问题时绿；旧未结束轮次和背景异步问题保留历史，不再永久覆盖新任务结束。真实审批与其他聊天的等待仍优先。监控断联或租约结束关灯，语音优先，唤醒显示白色跑马灯。监控中禁止上位机手动调灯。协议仍区分 unknown 与 idle，绿色是显示策略，不伪造状态。

正式默认构建仍关闭协议实验，不能直接用默认构建替代当前支持上位机的设备固件；隔离构建入口和显式参数见协议文档。当前设备已刷入支持五组 Wi-Fi 历史的无线隔离版及配套 5 MiB 模型，保留语音重配与 20 ms USB 过滤；此前 USB 隔离版曾通过 30 分钟连续更新。重配测试出现过一次用户确认的自动断连，原因未定位，不能据旧长测承诺当前固件长期稳定。换珠后红白黄经用户确认正常。状态源现修复快照与宿主证明的并发读取竞态；此前 3 次 unknown 缺少逐次原因，长期状态稳定和完整语音/监控/断线目视验收仍待补。没有自动启动的设备桥接服务；托盘隐藏会保留既有监控连接，真正退出才释放。2026-10-19 新版采集器已获用户信任，真实事件与用户观察确认运行红、结束绿、异步选项待回复黄及回答后恢复；更新后排查与修复记录见 [CodexMonitor](Tools/CodexMonitor/README.md#codex-更新后排查与本次修复--upgrade-troubleshooting)。五状态灯效的物理断电持久化仍待补验。

### 监控会话数量限制

| 范围 | 当前限制与处理 |
| --- | --- |
| 累计创建的聊天、磁盘历史记录 | 未设置固定数量上限；不因累计到第 17 个聊天而停止监控。历史暂未自动裁剪，仍受磁盘、内存和处理时间限制，不代表无限容量。 |
| 当前发给设备的监控视图 | 当前最多 16 个会话，按双方协议能力协商；包括参与显示的运行、等待、未知等条目及保留的最新结束记录，不是仅统计“正在运行”的聊天。 |
| 当前视图超限 | 报来源异常，不静默截断活动会话或审批；来源异常默认绿不代表完成。 |

新建聊天本身不会触发容量错误。启动前已过期且未接纳的历史不占当前名额，已确认结束的记录只保留最新一个显示；已接纳的运行/等待不会因为长时间没有新事件而被丢弃。2026-10-19 已修复把全部历史误算进 16 会话容量的问题，保留 17 个历史聊天的现场复测恢复正常，用户确认灯色恢复。完整逻辑与升级流程见 [历史容量排查](Tools/CodexMonitor/README.md#历史聊天超过设备容量导致来源异常)。

“电脑汇总所有聊天后只发送总状态”可作为取消这项固定会话限制的后续方案，当前尚未实现；本次修复没有提高设备上限。

设备 Codex 任务屏（2026-10-19，已刷隔离版、四卡协议及短时音频检查通过，用户确认刷新观感）：监控时切换为最多四个活动对话的 2×2 气泡，等待优先、稳定槽位、超四提示；本地模式或监控断联恢复原仪表盘。标题、状态和卡片采用区域缓冲刷新，常规更新不再逐条清屏。标题从本地 Codex 标题索引匹配，以中文文字位图经 USB/WSS 发往设备，不读取聊天正文。需要声明任务屏能力的新隔离固件，旧固件继续原有灯光功能。合成三/四卡演示约两分钟、125 个音频样本无丢帧或看门狗异常；30 分钟演示按用户要求提前停止，未完成长期验证。协议、隐私及失效边界见 [业务快照](Tools/DeviceBridge/README.md#业务快照--business-snapshots)。

## 快速开始 / Quick Start

### 环境要求 / Requirements

- VS Code + PlatformIO

- USB 数据线
- Arduino + ESP-IDF 双框架（由 PlatformIO 安装）；拉取 ESP-SR 子模块：`git submodule update --init --recursive`。
- 只使用 Windows 程序时，完整解压便携包并运行 `Omi.exe` 即可，无需安装开发工具；见 [快速开始](Tools/Desktop/QUICK_START.md)。

### 编译、烧录和串口监视 / Build, Upload, and Monitor

以下命令构建默认固件，**默认关闭 USB 桌面协议与无线服务**，不能直接替代当前支持上位机的设备镜像。要构建桌面/无线版本，先按 [隔离配置](Tools/DeviceBridge/README.md#构建与验证) 生成配置；应用与当前词表生成的模型需配套烧录。烧录前备份完整 Flash，并重新枚举实际串口。

在仓库根目录执行默认构建：

```powershell
cd Firmware
pio run
pio run -t upload
pio device monitor -b 115200
```

ESP32-S3 使用原生 USB CDC 输出串口日志。当前运行状态可以通过以下日志确认：

```text
[SYS] alive ms=... mic=ok wifi=offline
[TIME] NTP synchronized 2026-10-04 12:34
[MIC] frames=800 avg_abs=... rms=... peak=... noise=... threshold=... speech=no
```

当对着麦克风说话时，`rms` 和 `peak` 应明显上升，并可能出现 `speech=yes`。

首次没有保存 Wi-Fi 配置时，设备会启动配网热点并显示门户地址；使用手机连接热点后，在网页中选择附近 Wi-Fi 并填写密码即可完成配网。

Wi-Fi 现保存最近成功使用的 5 个不同 SSID（NVS，断电保留），同名网络更新密码，第 6 个成功连接的网络替换最久未成功使用的记录。启动优先尝试最近成功的网络；断线后按每组最多 20 秒依次重试，门户开启或超时后仍继续重试。初次启动会先尝试一轮已保存网络，运行中断线保留原 60 秒配网宽限期。升级会迁移驱动中尚存的最后一组凭据；以前已被覆盖的网络需重新配网一次。新固件已刷入并验证旧凭据迁移、旧网恢复及 90 秒音频健康采样；真实多网络自动切换、物理断电持久化和语音动作并行稳定性仍待实机验收。

联网后固件通过 `ntp.aliyun.com`、`pool.ntp.org` 和 `time.nist.gov` 获取时间，按 UTC+8 显示；首次同步失败每 10 秒重试，已同步后每 1 小时重新校时。主循环在音频处理前后刷新网络和时间状态，减少语音推理造成的 UI 延迟。只有 Wi-Fi 已连接且 NTP 已同步时才显示时间；Wi-Fi 断开或 NTP 尚未同步时，时间显示为 `--:--`，日期显示为 `----/--/--`，不会回退到编译时间。

## 温湿度补偿说明 / Sensor Compensation

AHT20 上电初期的读数通常接近环境值。随着 ESP32-S3、LCD 背光、电源区域和灯带持续工作，传感器所在 PCB 区域会升温，导致温度偏高；相对湿度也会因此表现为偏低。

当前固件采用针对本设备实测得到的经验补偿：温度约减 `4 °C`，湿度约加 `9 %RH`。这不是 AHT20 厂家提供的固定参数，只适用于当前 PCB、负载、背光、灯带亮度、供电和外壳条件。若这些条件改变，应重新进行现场校准。

> **English** — The temperature and humidity offsets are device-specific field calibration values, not sensor-datasheet constants. Recalibrate them if the thermal layout, load, lighting, power source, or enclosure changes.
